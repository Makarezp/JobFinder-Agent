### Ticket 008: Give each iTerm-tab viewer client its own tmux current-window pointer

#### Overview
`ItermTabViewer.reveal()` (`agentctl.py:675-706`) attaches every new iTerm tab to the run's shared tmux session with a plain `tmux attach`, then runs `select-window` inside it. Because a tmux session's "current window" is one pointer shared by every attached client, each new agent's `select-window` silently retargets every previously opened tab for that run onto the newest agent's window — a human can end up typing an answer into what they believe is Agent A's tab while it lands in Agent B's composer (reproduced twice live, see `work_organisation/probe/iterm-viewer-shared-window-bug.md`). The fix is to give each revealed tab its own independent current-window pointer via a tmux **grouped session**, so `select-window` inside one client's session can no longer affect any other client.

#### Implementation Steps
1. **`agentctl.py` — `ItermTabViewer.reveal()` (lines 675-706)**: Change the command it writes from
   `TMUX= tmux attach -t <target> \; select-window -t <handle>`
   to a grouped-session form:
   `TMUX= tmux new-session -t <target> -s <viewer-session-name> \; set-option destroy-unattached on \; select-window -t <handle>`
   - `new-session -t <target>` (the `-t` here is `new-session`'s "session group" flag, distinct from `attach -t`'s "session to attach" flag — verify the exact tmux 3.7b flag semantics before writing the command, since `new-session` also has `-s` for the new session's own name) creates a new session that shares the run's window list with `<target>` but has its own independent current-window pointer. Running `select-window` inside it will no longer change what any other client displays.
   - `set-option destroy-unattached on` must be scoped to the *new* grouped session, not the run's base session — check whether it needs `-t <viewer-session-name>` explicitly or whether it applies to the session created earlier in the same command chain by default. This makes tmux auto-kill the grouped session the moment its one client detaches (e.g. the human closes the iTerm tab without the agent being closed first), so grouped sessions cannot accumulate in `tmux list-sessions` from that path.
   - The env-clearing `TMUX=` prefix, the `\;` shell-escaping (not a bare `;` — see the existing comment above line 686 and `test_reveal_uses_the_exact_match_target_not_the_bare_run_id` / the hostile-run-id test for why), and both existing `_shell_quote` / `_applescript_escape` layers stay exactly as they are — only the tmux subcommand sequence changes, not the quoting machinery around it.
2. **`agentctl.py` — viewer session naming**: Add a helper (near `tmux_target`, ~line 725) that derives a unique, tmux-safe session name for the grouped session from `run` and `handle`, e.g. `f"{run}--viewer--{handle}"` with `handle`'s leading `@` handled explicitly (confirm tmux session names may contain `@`; strip or replace it if not). `handle` is a tmux window id, unique server-wide at the time `reveal()` is called (`agentctl.py:1512`, called once per spawn), so this name will not collide across concurrent reveals. Do not reuse the run name alone or any other non-unique value — a second agent in the same run must get a session name distinct from the first agent's.
3. **No changes to `close_agent` / `close_run` / `TmuxBackend.kill_run`**: Trace why before touching them, so this doesn't get "fixed" a second time. `close_agent` (`agentctl.py:1916-1959`) calls `backend.kill(meta.handle)`, i.e. `kill-window -t handle` (`agentctl.py:862-863`). `kill-window` removes that window from every session in its group, including the grouped viewer session. A tmux session that reaches zero windows is destroyed automatically by tmux itself — this is unconditional tmux behavior, not something `agentctl` implements. So once an agent's window is killed, its grouped viewer session (if any) disappears on its own, before `close_run`'s subsequent `backend.kill_run(paths.run)` (`agentctl.py:883-885`, `kill-session -t run`) even runs. Confirm this holds under tmux 3.7b (the version the rest of this file's comments say has been verified against) with a manual reproduction before relying on it in the implementation.
4. **Tests — `.agent/skills/agent-tabs/tests/test_viewer.py`**: Every existing test that inspects the exact command string `reveal()` builds will break and must be rewritten for the new `new-session -t ... -s ... \; set-option destroy-unattached on \; select-window -t ...` sequence, not just patched to pass:
   - `test_reveal_round_trips_a_hostile_run_id_through_both_escaping_layers` (line 44): rebuild `intended` to match the new multi-`\;` command; keep asserting the hostile run id (`'My "Run"\\Two'`) round-trips through both escaping layers, and keep the existing assertions that a bare `;` never appears unescaped (`" ; " not in command`) — this must now hold across *two* `\;` separators, not one.
   - `test_reveal_uses_the_exact_match_target_not_the_bare_run_id` (line 78): keep asserting `=cvv` (exact-match target) is what follows the *first* tmux subcommand's `-t`, now `new-session` instead of `attach`.
   - Add a new test asserting two `reveal()` calls with the same `run` but different `handle`s produce two different session names in the emitted command (the collision case this bug is actually about) — extract the session name the same way `_extract_command` already extracts the write-text payload.
   - Add a new test asserting the emitted command contains `set-option destroy-unattached on` scoped to the grouped session, not the base run session.
   - `test_reveal_raises_viewer_error_on_nonzero_exit_carrying_stderr`, `test_null_viewer_is_a_no_op_for_any_input`, `test_get_viewer_*`, `test_both_viewers_satisfy_the_protocol` (lines 91-122): these don't inspect the command string and should need no changes; confirm they still pass unmodified.
5. **Manual reproduction (this is the part unit tests cannot cover)**: Repeat the exact steps from `work_organisation/probe/iterm-viewer-shared-window-bug.md` section 4 — spawn two agents into the same run with `--viewer iterm-tab`, switch back to the first tab, and run `tmux list-clients -F "#{client_tty} session=#{client_session} window=#{window_id}"`. Confirm the two clients now report two different `session=` values (the grouped sessions) and each still shows its own agent's window. Then close one agent with `agentctl close` (not force) and confirm via `tmux list-sessions` that its grouped viewer session is gone, not orphaned.

#### Explicit Constraints & Warnings
- **Do not solve this by tracking grouped session names in `agentctl`'s own state and killing them explicitly from `close_agent`/`close_run`.** That duplicates a lifecycle tmux already gives you for free (windows-to-zero auto-destroys the session) and adds a second source of truth that can drift from tmux's actual state. Only reach for explicit tracking if the manual reproduction in step 5 shows the auto-destroy behavior does not actually hold.
- **Do not change `TmuxBackend.open`, `.kill`, `.alive`, `.list_handles`, or `.kill_run`.** The bug and its fix are entirely inside `ItermTabViewer.reveal()`; `Backend` must stay ignorant of viewers per the existing docstring on the `Viewer` protocol (`agentctl.py:613-620`: "a viewer must never call `backend.*` directly, and `Backend` must never grow a `reveal` method"). This ticket does not revisit that boundary.
- **Do not touch the quoting/escaping layers** (`_shell_quote`, `_applescript_escape`, the `TMUX=` prefix, or the `\;` vs bare `;` handling). Every one of those exists because of a previously-caught live bug (see the comments at `agentctl.py:659-673` and `679-689`); this ticket only changes which tmux subcommands are chained together, not how the resulting line reaches the shell or tmux.
- **Verify `new-session -t <target> -s <name>`'s exact flag semantics against tmux 3.7b before writing the final command**, including whether `-t` on `new-session` is even the right flag for "join this existing session's group" (double-check current tmux docs/behavior; do not assume the write-up's sketch of the command was already correct — it was explicitly left undecided).
- **Session names must be derived from data already available inside `reveal(run, handle)`** — do not thread a new agent-name parameter through the `Viewer` protocol to build the session name; `handle` is already unique per call and sufficient.
- Do not attempt to fix `NullViewer` or add any new viewer — this ticket is scoped to `ItermTabViewer` only.

- [Automated] A new `test_viewer.py` test proves the hostile-run-id round-trip (backslashes and double quotes in the run id) still survives both escaping layers across the new multi-`\;` command, and that no unescaped bare `;` appears anywhere in the emitted text.
- [Manual] Spawn two agents into one run with `--viewer iterm-tab`. Switch to the first agent's tab. It must still show the first agent's window, not the second's. `tmux list-clients` must show the two iTerm-tab clients attached to two different sessions, each with the correct `window=`.

- [Manual] Close the first agent with `agentctl close` (graceful, not `--force`). Run `tmux list-sessions` afterward and confirm no grouped viewer session for that agent remains.
- [Manual] Run `agentctl close-run` on a run with two iTerm-tab-viewed agents still open. Confirm both grouped viewer sessions and the run's base session are all gone from `tmux list-sessions` afterward.
