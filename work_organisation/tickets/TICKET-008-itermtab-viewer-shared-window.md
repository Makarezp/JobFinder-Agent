### Ticket 008: Give each iTerm-tab viewer client its own tmux current-window pointer

> **Revision note:** This ticket was reviewed against live tmux 3.7b before implementation (review-008, 2026-08-10). The original draft's core mechanism (grouped sessions) was confirmed correct, but its claim that `close_agent`/`close_run` needed no changes was **false** and would have broken run teardown. This revision incorporates every required correction from that review; the findings (`F1`–`F9`) are cited inline so the reasoning is traceable, not just the conclusion.

#### Overview
`ItermTabViewer.reveal()` (`agentctl.py:675-706`) attaches every new iTerm tab to the run's shared tmux session with a plain `tmux attach`, then runs `select-window` inside it. Because a tmux session's "current window" is one pointer shared by every attached client, each new agent's `select-window` silently retargets every previously opened tab for that run onto the newest agent's window — a human can end up typing an answer into what they believe is Agent A's tab while it lands in Agent B's composer (reproduced twice live, see `work_organisation/probe/iterm-viewer-shared-window-bug.md`). The fix is a tmux **grouped session** per revealed tab, verified live to give each client its own independent current-window pointer while sharing the run's window list — but grouped sessions change what "the run's tmux state" consists of, which means teardown (`kill_run`) and per-agent close (`close_agent`) must change with it, not stay untouched.

#### Implementation Steps
1. **`agentctl.py` — `ItermTabViewer.reveal()` (lines 675-706)**: Change the command it writes from
   `TMUX= tmux attach -t <target> \; select-window -t <handle>`
   to:
   `TMUX= tmux new-session -t <target> -s <viewer-session-name> \; set-option -t <viewer-session-name> destroy-unattached on \; select-window -t <handle>`
   - Verified on tmux 3.7b: `new-session -t <target>` is the session-**group** flag (man page: *"If `-t` is given, it specifies a session group"*), joins the new session to `<target>`'s group sharing its window list, and gives the new session its own independent current-window pointer — confirmed with two live grouped-session clients, each showing its own agent's window, with the base session's current window never retargeted.
   - `set-option` **must** carry an explicit `-t <viewer-session-name>`, shell-quoted the same way every other embedded value in this command is. The un-targeted form happens to land on the newly-created session on 3.7b today, but that is an ordering accident of the `\;` chain, not a documented guarantee — if it ever lands on the run's *base* session instead (a tmux version change, a reordered chain, an inserted command), `destroy-unattached on` would be set on the run itself and the entire run, every agent in it, would be destroyed the instant the last human tab detaches. Pay the one extra token; do not rely on default scoping for a mistake this expensive.
   - The derived `<viewer-session-name>` **must be shell-quoted** (`_shell_quote`) exactly like `target` and `handle` already are — it is built from `run`, which carries the same hostile-input risk the target does (see the existing hostile-run-id test).
   - tmux session names may contain `@` (verified: `vw--@1333` created and targeted with no stripping needed) — no character substitution needed for the handle's leading `@`.
   - The `TMUX=` prefix, the `\;` shell-escaping (never a bare `;`), and both existing `_shell_quote` / `_applescript_escape` layers stay exactly as they are; verified that adding a second and third `\;` introduces no new instance of the three previously-fixed live bugs (`_shell_quote` is unconditional and covers the whole line; `" ; " not in command` still holds across N separators).
   - **Do not use `new-session -A`** to dodge a same-name collision (see step 6) — `-A` attaches to the existing session instead of creating a new one, putting two tabs back on one shared current-window pointer: the exact bug this ticket exists to remove, reintroduced on the retry path.
2. **`agentctl.py` — viewer session naming**: Add a helper (near `tmux_target`, ~line 725) that derives a session name from `run` and `handle`, e.g. `f"{run}--viewer--{handle}"`. `handle` is a tmux window id, unique server-wide at the time `reveal()` is called (`agentctl.py:1512`, called once per spawn), so two concurrent reveals in one run cannot produce the same name. This name is only ever used as a *creation* argument (`new-session -s`), never to re-locate a session later — see step 3's constraint on why.
3. **`agentctl.py` — `TmuxBackend.kill_run` (lines 883-885) must change.** This is a correction to the original draft, not an optional addition: a grouped viewer session shares the base session's entire window list, including the permanent `__root__` placeholder window that `TmuxBackend.open` always creates (`agentctl.py:783`) and that `close_agent` never kills (it belongs to no agent; it is filtered out of `list_handles` at line 879 for the same reason). That means a grouped session **never** reaches zero windows through per-agent `kill-window` calls alone — it always still holds `__root__`. Verified live: after killing every agent window in a run, a grouped viewer session still shows `2 windows (attached)`, and plain `kill-session -t <run>` (no group flag) destroys *only* the base session — per the tmux man page, `kill-session` closes windows linked to the given session "and no other sessions" — leaving every grouped viewer session, `__root__`, and any agent window that failed to die during per-agent close, alive and orphaned forever. `apply_reap` (`agentctl.py:2009-2010`) calls the same `kill_run` and inherits the identical hole.
   Fix: `kill-session -g -t <target>` — the `-g` flag destroys every session in the target's group, verified to correctly tear down the base session plus all grouped viewer sessions plus every remaining window, and verified safe to pass unconditionally even when the session has no group (no error).
   ```python
   def kill_run(self, run: str) -> None:
       if self._session_exists(run):
           # -g kills every session in the run's session group. Viewer clients
           # attach via grouped sessions, and kill-session without -g destroys
           # only the base session -- the group's windows (including
           # __root__) and any grouped viewer sessions survive and the run is
           # not actually torn down.
           self._tmux("kill-session", "-g", "-t", self._target(run))
   ```
   This does not violate the `Viewer`/`Backend` boundary (`agentctl.py:613-620`): a session group is a tmux concept, not a viewer concept, and "tear down the run's session group" is a strictly more correct definition of "tear down the run" than "tear down one session that happens to share the run's name" — it holds even for a grouped session a human created by hand. `Backend` remains ignorant of viewers; it merely stops being ignorant of session groups. Add a `FakeBackend`/backend-fake test asserting `kill_run` invokes `kill-session` with `-g` in its argv.
4. **`agentctl.py` — decide and implement what happens to a viewer's tab when its agent is closed.** The original draft assumed a killed agent window causes its grouped session to vanish; verified false (step 3). What actually happens: tmux moves the still-attached client to the session's last-window pointer, which is `__root__` today only because nothing else has ever selected a window in that session — but the moment a human uses ordinary tmux navigation inside their own tab (`C-b n`, `C-b w`), that pointer can point at a **live sibling agent's window**, and a subsequent `close_agent` on the first agent then silently drops the human's tab onto that sibling's composer with no visual signal — the same failure class this ticket exists to eliminate, narrowed but not removed.
   Implement the preferred fix: add `conceal(run: str, handle: str) -> None` to the `Viewer` protocol (`agentctl.py:611-622`), a no-op on `NullViewer`, and call `viewer.conceal(paths.run, meta.handle)` from `close_agent` (`agentctl.py:1916-1959`) right where `backend.kill(meta.handle)` already runs (lines 1943 and 1951 — both the `force` and graceful branches kill the window and must both conceal). `ItermTabViewer.conceal()` implementation:
   - Run `tmux list-sessions -F '#{session_name}\t#{session_group}'`, filter to the row whose `session_group` equals `run`'s session name and whose own name is not the base session itself, and `kill-session -t` that session by the *name tmux just reported*, not by rebuilding `f"{run}--viewer--{handle}"` (see step 6 for why reconstruction is unsafe). There may legitimately be zero matching rows (viewer was `none`, or the tab was already closed) — that is not an error.
   - This introduces no second source of truth: the session is discovered from tmux's own live output each time, never cached or written to `agentctl`'s state.
   - Wrap the same way `backend.kill`/`backend.send` calls already are in `close_agent` (`_suppressed()`) — concealing a tab must never block or fail a close.
5. **Tests — `.agent/skills/agent-tabs/tests/test_viewer.py`**: Every existing test that inspects the exact command string `reveal()` builds must be rewritten for the new multi-`\;` sequence, not just patched to pass:
   - `test_reveal_round_trips_a_hostile_run_id_through_both_escaping_layers` (line 44): rebuild `intended` for the three-subcommand chain; keep the hostile run id (`'My "Run"\\Two'`) round-tripping through both escaping layers; keep asserting no bare `;` appears, now across *three* `\;` separators.
   - `test_reveal_uses_the_exact_match_target_not_the_bare_run_id` (line 78): keep asserting `=cvv` follows the *first* subcommand's `-t`, now `new-session` instead of `attach`.
   - New test: two `reveal()` calls with the same `run`, different `handle`s, produce two different session names in the emitted command.
   - New test asserting `set-option`'s target is the *viewer session name*, not the run's base target — assert the token, not a substring: `argv[argv.index("set-option") + 2] == <viewer session name>` and separately assert `tmux_target(run)` does not appear as `set-option`'s target. (A substring check like `"set-option destroy-unattached on" in command` cannot distinguish the correct scoping from the catastrophic one described in step 1 — do not write that test.)
   - New test asserting the derived session name is passed through the same shell-quoting as `target`/`handle` (e.g. reuse the hostile-run-id fixture and confirm the session name argument round-trips too).
   - New tests for `conceal()`: mirrors the `reveal()` command-construction tests — asserts the `list-sessions`/`kill-session` shape via the injected runner, and that `NullViewer.conceal()` is a no-op.
   - `test_reveal_raises_viewer_error_on_nonzero_exit_carrying_stderr`, `test_null_viewer_is_a_no_op_for_any_input`, `test_get_viewer_*` (lines 91-116) need no changes. `test_both_viewers_satisfy_the_protocol` (line 119) **does** need updating: the `Viewer` protocol now includes `conceal`, so this test's coverage of "both viewers satisfy the protocol" must exercise the new method too.
6. **String tests cannot see the defects this ticket is actually about — add live-tmux tests.** `test_viewer.py` never shells out to real tmux by design (module docstring), so none of the string tests above can observe whether teardown actually leaves nothing behind, whether `select-window` actually stays contained to one client, or whether `kill_run` actually destroys a run. Add, using this repo's existing live-tmux test infrastructure:
   - A teardown test: build a run session + two agent windows + two grouped viewer sessions exactly as the emitted commands would, run the equivalent of `close_run`, then assert no session in the group survives and neither agent window survives. This must fail against `kill_run`'s current (pre-step-3) implementation and pass after the `-g` change — write it before the fix if practical, to prove it actually catches the regression.
   - A "the fix fixes the bug" test: two grouped sessions, `select-window` run in one, assert the *other* session's current window is unchanged and the base session's current window is still whatever it was before (`__root__`), never retargeted.
   - A base-session option test: after building a grouped session, assert `show-options -t <base target> destroy-unattached` is empty — i.e. the option never leaked onto the run's own session (step 1's asymmetric-failure concern).
   - Locate viewer sessions in every live test **by `#{session_group}` filtering, never by reconstructing `f"{run}--viewer--{handle}"` as a `-t` target** — tmux 3.7b stores a literal backslash in a session name doubled (`'a\b'` is stored and reported as `a\\b`) so the original string cannot address it again, and a name containing `:` or `.` is accepted at creation but re-parsed as `session:window` / consumed as a separator when later used as a target — both verified live, both making a reconstructed target silently fail to find the session it was built to describe. `conceal()` (step 4) is written against this constraint already; the tests must be too.
7. **Manual reproduction**: Repeat the exact steps from `work_organisation/probe/iterm-viewer-shared-window-bug.md` section 4 — spawn two agents into the same run with `--viewer iterm-tab`, switch back to the first tab, and run `tmux list-clients -F "#{client_tty} session=#{client_session} window=#{window_id}"`. Confirm the two clients report two different `session=` values, each still showing its own agent's window. Then:
   - Run `tmux show-options -t =<run> destroy-unattached`; it must print nothing (confirms step 1's targeted `set-option` never touched the base session).
   - Close one agent with `agentctl close` (graceful, not `--force`). Confirm the human's tab for that agent either closed (if `conceal` fired) — check per step 4's implementation — and that it never lands on the other, still-live agent's window.
   - Run `agentctl close-run` on a run with two iTerm-tab-viewed agents still open. Confirm via `tmux list-sessions` that the base session and both grouped viewer sessions are all gone.

#### Explicit Constraints & Warnings
- **Do not store or cache grouped-session names in `agentctl`'s own state** (a file, a dict, agent metadata). Every lookup after creation must go through live `tmux list-sessions`/`#{session_group}` filtering (steps 4 and 6). Session names are for `new-session -s` at creation time only.
- **Do not skip step 3's `kill_run` change.** The original version of this ticket forbade changing `TmuxBackend.kill_run`, on the mistaken belief that per-agent window kills would empty a grouped session on their own. That is false — verified live, a grouped session always retains `__root__` — and skipping this step means `close-run` and `reap` silently stop destroying runs the moment any agent has ever been viewed with `iterm-tab`. This is the one part of the original draft that must not be implemented as first written.
- **Do not change `TmuxBackend.open`, `.kill`, `.alive`, or `.list_handles`.** Only `.kill_run` needs the group-aware `-g` flag (step 3); the rest of `TmuxBackend` is unaffected by grouped sessions.
- **`Backend` still must not gain a `reveal`-shaped method**, and viewer session lookups belong in `ItermTabViewer`, not `TmuxBackend` — `conceal()` shells out to `tmux` directly the same way `reveal()` already does, exactly parallel to how the existing code is structured, not routed through `Backend`.
- **Do not touch the quoting/escaping layers** (`_shell_quote`, `_applescript_escape`, the `TMUX=` prefix, or `\;` vs bare `;`) beyond applying `_shell_quote` to the new session-name argument. Every one of those exists because of a previously-caught live bug (`agentctl.py:659-673`, `679-689`).
- **Verify `new-session -t <target> -s <name>`'s flag semantics and `-g`'s group-kill behavior against tmux 3.7b** (the version this file's other docstrings claim verification against) before relying on either in the implementation — both are now confirmed correct by the review that produced this revision, but re-confirm on whatever tmux binary CI/dev machines actually run, since this ticket's entire premise is that undocumented-feeling tmux behavior deserves live verification, not analogy.
- **Do not fold in the pre-existing, unrelated bug that run ids containing a backslash already break `TmuxBackend.open`/`._session_exists` today** (independent of this ticket — a second agent window cannot even be opened into such a run, and the existing hostile-run-id test in `test_viewer.py` certifies escaping for a run that cannot actually be hosted by `TmuxBackend`). File that separately; it is out of scope here.
- Do not attempt to fix `NullViewer` beyond adding the new no-op `conceal`, and do not add any new viewer type — this ticket is scoped to `ItermTabViewer` and the `Viewer` protocol's `conceal` addition only.

#### Acceptance Criteria
- [Automated] `test_viewer.py`'s command-string tests pass against the new three-subcommand `reveal()` sequence, including: two `reveal()` calls in the same run producing distinct session names; `set-option`'s target being the viewer session name and specifically *not* the run's base target (token assertion, not substring); the derived session name passing through the existing shell-quoting layer.
- [Automated] New live-tmux tests (step 6) pass: a full teardown sequence leaves no session in the run's group and no surviving agent window; `select-window` inside one grouped session never changes another grouped session's or the base session's current window; the base session never has `destroy-unattached` set; `TmuxBackend.kill_run`'s argv contains `-g`.
- [Automated] New `conceal()` tests confirm the emitted `list-sessions`/`kill-session` shape via the injected runner, and that `NullViewer.conceal()` is a no-op.
- [Manual] Spawn two agents into one run with `--viewer iterm-tab`. Switch to the first agent's tab — it must still show the first agent's window. `tmux list-clients` shows the two clients attached to two different (grouped) sessions, each with the correct `window=`.
- [Manual] `tmux show-options -t =<run> destroy-unattached` prints nothing after both tabs are open.
- [Manual] Type text into the first agent's tab; confirm via that agent's own transcript that the text was delivered to it, not to the second agent.
- [Manual] Close the first agent with `agentctl close` (graceful). Confirm the behavior matches step 4's implemented `conceal()` (tab closes / detaches) and never lands on the second, still-live agent's window.
- [Manual] Run `agentctl close-run` on a run with two iTerm-tab-viewed agents still open. Confirm via `tmux list-sessions` that the base session and both grouped viewer sessions are all gone afterward.

#### Follow-ups (explicitly out of scope for this ticket)
- Run ids containing a backslash already break `TmuxBackend.open`/`_session_exists` independent of this ticket, and the existing hostile-run-id test in `test_viewer.py` certifies a run tmux cannot actually host one layer deeper than the test checks. File separately: either validate run ids at entry or fix targeting.
- `work_organisation/probe/iterm-viewer-shared-window-bug.md` §5's documented workaround ("manually `tmux attach -t <run>:<window>` is not retargeted by subsequent spawns") is incorrect — verified live, a manually-attached plain client still shares the base session's current-window pointer and is retargeted exactly like an `iterm-tab`-revealed one. Fix that section as part of executing this ticket (it is the document this ticket cites as its evidence base and is actively misleading readers today): replace it with a verified-safe manual workaround, e.g. `TMUX= tmux new-session -t '=<run>' -s "$(whoami)-manual-$$" \; select-window -t <window>`.
- `destroy-unattached on` makes an accidental `C-b d` in a viewer tab unrecoverable except via a hand-typed `tmux new-session -t`; consider a small `agentctl reveal <agent>` subcommand to re-open a tab, or `destroy-unattached keep-last` if that tradeoff is judged wrong. Not needed for this ticket to close the misdirection bug.
