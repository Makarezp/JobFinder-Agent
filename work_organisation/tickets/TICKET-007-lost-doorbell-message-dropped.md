# Ticket 007: Fix the Lost-Doorbell Measurement Instrument, Then Answer C014 (Real-Worker Drop vs. Harness Teardown Race)

## Overview

`C014`'s resilience guarantee is that a lost/garbled doorbell keystroke should cost nothing, because the instruction is still sitting in the worker's inbox and `WORKER.md` requires reading unread files "lowest number first" at the start of every turn. `COVERAGE.md` currently marks `C014` **covered / no-finding** on the strength of one `probe.py run B002 --trials 1` pass (`rate: 1.0`) — thin evidence for a `Covered` verdict on its own. A separate, hand-run real-Haiku trial (preserved in `work_organisation/probe/explore-lostdoorbell-c014/`) shows the worker replying to message A and message C but never echoing B's token (`TOK-5WRF`).

That preserved trial does **not** establish a real drop. `bus.jsonl` for the third turn shows `turn_start` (seq 11) and `reply` (seq 12) but **no `turn_end`** — the harness force-killed the SUT (seq 13) 0.822s after the reply, which is shorter than the 1.7–3.7s the worker kept working past `reply` in each of the two prior, completed turns. This is indistinguishable from the `B001`/`B003` harness-verdict findings this spec explicitly (and, on inspection, incorrectly) claimed not to resemble. Worse, this isn't unique to the preserved trial: `runner._run_trial` reads `outbox_messages` and grades immediately after the first post-C `reply`, with no wait on `turn_end`, for every trial `B002` ever runs. So the brief that this ticket's own measurement step relies on has the identical defect baked in — it cannot currently distinguish "worker dropped B" from "worker was about to sweep its inbox and reply again, but got killed first." Nobody has yet observed a worker actually drop a message; what has been observed is a worker killed inside the window where a second reply would land.

This ticket's job is therefore two-stage: first fix the measurement instrument (a two-line change to `runner.py`, using an existing wait primitive) so `B002`'s rate means what the ticket needs it to mean, then use the corrected instrument to determine whether the lost-doorbell guarantee holds at a statistically meaningful trial count, and only then decide whether a wording or delivery-mechanism change is warranted.

The former is the only artifact of the original miss and cannot be regenerated by re-running the brief (there is no `explore`-intake oracle path in `probe/lib/oracle.py`). `git add` and commit both directories before touching anything else — a constraint to "preserve" evidence that isn't in version control is not a control.

### 1. Correct the record in this ticket and in the spec

- In `work_organisation/probe/explore-lostdoorbell-c014/README.md` §1 (Evidence), strike any claim that "the final turn completed normally (not truncated)." Replace with: the trial is **inconclusive** — `turn_end` never fired for turn 3 (no Stop hook event in `bus.jsonl`), and the SUT was killed 0.822s after the reply, faster than the 1.7–3.7s post-reply windows observed in the same transcript's completed turns. Reclassify the `Target` note to include a third candidate cause: harness teardown racing the worker's turn (this is currently the most likely explanation, not real-worker or single-trial-methodology).
- Note explicitly that the mechanical inbox/bus plumbing behaved exactly as documented: `write_lost_doorbell` (`runner.py:89-100`) uses exclusive `"x"` creation plus `fsync`, emits no `message_sent` event, and B's token genuinely appears in no outbox file. Only the *interpretation* of that absence (as a confirmed drop rather than an inconclusive kill) was wrong.

### 2. Fix the harness before measuring anything (blocking prerequisite)

In `.agent/skills/agent-tabs/probe/lib/runner.py`, `_run_trial` reads `outbox_messages` immediately after `_exercise` returns, and `_exercise`'s `B002` path (`_lost_doorbell`) ends by calling `_wait_for_reply`, which itself returns on the *first* `type=reply` event after the watermark — there is no wait on `turn_end`, no settle window. Add a wait on `agent=worker,type=turn_end` (bounded by `brief.wait_timeout`) after the final `_wait_for_reply` call inside `_lost_doorbell` (or immediately after it returns in `_run_trial`, before `outbox_messages` is read), using the same `agentctl wait --until` predicate `_wait_for_bootstrap` and `_wait_for_reply` already use — this is a two-line addition, not a new mechanism. This applies to both the target (`B002`) and control (`B002-control`) exercise paths, since `_lost_doorbell(control=True)` ends in the same unguarded `_wait_for_reply` call.

Without this fix, no rate produced by step 5 below is interpretable, and a low rate would risk being misattributed to `WORKER.md` wording rather than to this harness gap.

### 3. Evaluate both fix levers, not just wording

Do not assume the fix, if needed, is prompt wording. Look at what `agentctl.py`'s `doorbell_text` (line 1249) actually sends: `f"[orchestrator] new instruction: {inbox_path}"` — a pointer to one specific file. In the preserved trial, the worker replied with exactly the token from the file the doorbell named, which is the model following a concrete imperative pointer, not ignoring `WORKER.md`'s general "read unread files" instruction. A cheaper, more robust lever than wording may be making the doorbell state the backlog, e.g. `f"[orchestrator] new instruction: {inbox_path} ({n} unread files in {inbox_dir}, read all lowest-number-first)"` — `_deliver` already has `paths` and `agent`, so counting unread files is a directory scan away. If step 6 finds a confirmed gap, compare this delivery-mechanism change against a wording change and prefer whichever measures better; do not foreclose the code-level option.

### 4. Pre-register the decision rule and the real budget before running anything

`probe.py run B002` runs the **control brief at the same trial count first, then the target** (`run_brief`, lines 45-66) — at the brief's default `trials: 10`, that is **20 real Haiku SUTs, not 10**, at roughly 66s/SUT (from the existing single-trial ledger entry: `wall_seconds: 131.923` for 1 control + 1 target), i.e. ~22 minutes per `run B002` invocation, not the "~2-3 minutes" previously assumed.

Statistical power at `trials: 10` is too low to trust a clean run: with 0 failures in 10 trials, the 95% upper bound on the true drop rate is ~25.9% (Clopper-Pearson). A true 10% drop rate would still produce "0 failures in 10" 35% of the time. Ruling out a 10% drop rate at 95% confidence needs **30 trials**, not 10.

Pre-register before running: fix step 2 first, then run **30 trials** if the budget allows (60 SUTs total including control, ~66 minutes). Zero failures at n=30 ⇒ record "drop rate ≤10% at 95% confidence," not "covered." One or more failures ⇒ confirmed gap, proceed to step 6. If 30 trials is unaffordable, run the brief's default 10 and record the honest bound ("clean at n=10, drop rate ≤25.9% at 95% confidence") — do not let `COVERAGE.md` say `Covered` on that basis, and do not let a control-brief flake (which aborts the whole run via `HarnessError` before the target trials execute, per `run_brief` line 61-62) count against whatever total-run budget is set; a control abort produces no ledger entry and should be retried, not treated as a spent trial.

Also note for interpretation: `grade_tokens` unions tokens across the *entire* outbox, so `B002` never checks that B's token was reported in the *same turn* it should have been — it only checks the token appeared somewhere before teardown. This is more lenient than the C014 claim text ("re-reads its inbox at the start of every turn"), so a passing rate doesn't prove per-turn attribution, only eventual delivery. State this in whatever record captures the outcome.

## Explicit Constraints & Warnings

- **Fix the harness (step 2) before running any measurement.** A rate produced by the unfixed `_run_trial`/`_lost_doorbell` path cannot distinguish a real drop from premature teardown — this is not optional groundwork, it is the precondition for every later step being meaningful.
- **Do not treat the doorbell/delivery-mechanism code as off-limits.** The original assumption that "the fix surface is instructional wording, not the inbox/bus code path" is wrong: `doorbell_text` naming one specific file is a plausible root cause in its own right and should be evaluated alongside wording, per step 3.
- **Do not run `probe.py run B002` more than the two times this ticket calls for** (step 5 measure, step 8 re-measure), excluding reruns caused by a control-brief `HarnessError` abort, which produce no data and don't count against this cap.
- **Do not treat a clean run at any trial count below ~30 as proof of a guarantee.** Report the statistical bound (see step 4), not a bare "covered."
- **If `WORKER.md` is edited, `claims.jsonl` must be hand-corrected** for C014 and the four claims anchored below it (C015-C018) — see step 7. Skipping this makes the ticket's own coverage acceptance criterion unsatisfiable.
- **Preserve the existing evidence directories** (`explore-lostdoorbell-c014/`, `explore-20260808T170211424180Z-c002/`) by committing them in step 0. They cannot be regenerated.
- **If the rate stays low even after a fix is applied**, do not iterate on wording indefinitely. Document in `README.md`/`COVERAGE.md` that this is an inherent haiku-model instruction-following limit under multi-unread-file turns, distinct from the delivery-mechanism lever, which should be tried first.
